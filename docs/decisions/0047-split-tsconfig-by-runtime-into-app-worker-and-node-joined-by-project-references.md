# ADR-0047: tsconfig は実行環境ごとに app・worker・node の 3 つに分け、ルートの tsconfig.json から project references でつなぐ

- Status: Accepted
- Date: 2026-11-03
- 関連: ADR-0004 (ツールチェーンを Vite+ に寄せる)、ADR-0055 (client から server の module を import させない)

## Context

このテンプレートのコードは、次の 3 つの実行環境で動く。

| 実行環境           | 置き場所                                                                                                                                                                              |
| ------------------ | ------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------- |
| ブラウザ           | `src/` のアプリのコード、`pages/*.tsx` (Worker の SSR でも動く)、ブラウザテストと story                                                                                               |
| Cloudflare Workers | `routes/`、`middleware/`、`crons/`、`queues/`、`db/`、`email/`、`durable-objects/`、`pages/**/*.server.ts`・`*.server.tsx`、`src/**/*.server.ts`・`*.server.tsx`、`auth.ts`、`env.ts` |
| Node.js            | `scripts/`、`tooling/`、`vite.config.ts`、`void.config.ts`、`.storybook/main.ts`、unit のテスト                                                                                       |

この表は動く場所の区分で、tsconfig の区分とは一致しない。テストと story は、ブラウザと Node.js のどちらで走るものも、置いたディレクトリで tsconfig が決まる (Decision の境界の判断)。

1 つの tsconfig に全部を入れると、次の 2 つがぶつかる。

- Void の docs「Type Safety」の Setup は `types: ["void/env"]` を求める。`void/env` の型 (`void/dist/runtime/env-public.d.mts`) の 1 行目は `/// <reference types="@cloudflare/workers-types" />` で、Workers の型を program 全体へ読み込む。同じ triple-slash は `void/dist/runtime/` の `email`・`handler`・`live`・`live-server`・`sandbox`・`sandbox-container` の型にもある (Void 1.4.0)
- Workers の型は HTMLRewriter の `Element` を宣言し、DOM の `Element` に merge される。1 つの tsconfig で `void/env` を足すと、`vp check` が 16 件のエラーで落ちた (2026-11-01、Void 1.4.0。型検査は vite-plus 1.4.0 の oxlint-tsgolint 7.0.2004)。DOM の `append` の TS2345 が 8 件と、`Buffer` が `any` になる `typescript/no-unsafe-*` が 8 件

tsconfig を分けても、server のファイルは次の経路で app の program に入る。入ったファイルが上の subpath を import すると、Workers の型が app に入り、DOM の `append` が TS2345 で落ちる (2026-11-03、Void 1.4.0、`tsc --explainFiles` で経路を確かめた)。

| 経路                                                                                                   | 入るファイル                                      |
| ------------------------------------------------------------------------------------------------------ | ------------------------------------------------- |
| `.void/routes.d.ts` の `typeof import(...)` (`packages/void/src/codegen/route-types.ts`)               | action を持つ `pages/**/*.server.ts`、`routes/**` |
| ページの `import type { Props } from "./x.server"` (Void の docs「Type Safety」の Loader → Page Props) | loader を持つ `pages/**/*.server.ts`              |
| 上の 2 つで入ったファイルの import                                                                     | `src/**/*.server.ts`                              |
| `.void/env.d.ts` の `typeof import("../env.ts")` (`packages/void/src/codegen/env-types.ts`)            | `env.ts`                                          |

- 4 つ目は `env.ts` を置くと `void prepare` が `.void/env.d.ts` を書き、`.void/tsconfig.json` の `files` に足す (`packages/void/src/codegen/project-tsconfig.ts`)。`env.ts` は docs「Environment variables」どおりに `void/env` から `defineEnv` を import するので、app のどのファイルも `void/env` を import していなくても落ちる
- Void の docs は、これらの subpath を上の経路に入るファイルで使う。action で `void/handler` の `ValidationError` (「Actions & Forms」)、route や action で `void/email` の `sendEmail` と、テストで `void/email/testing` (「Sending Email」)、`src/live.ts` で `void/live` の `defineLiveStream` (「Live Event Streams」)、route で `void/sandbox` の `getSandbox` (「Sandboxes」)。`ValidationError` は `void` の root から export されない

型検査は `vp check` が tsrs の `tsrs-lint` で回す (`docs/guides/dependencies-and-toolchain.md`「`typescript` を直接の依存に置かない理由」)。tsrs-lint は、ファイルごとに、そのファイルを割り当てた tsconfig の program で検査する (tsrs の `tools/tsgolint/README.md`「Type checking in the lint run」: "each is checked in the tsconfig program it maps to")。割り当ての先は、ルートの `tsconfig.json` の `references` から探す (2026-11-24、vite-plus 1.7.0 の tsrs 7.1.0-beta.tsrs2。案 A'' の probe で、`references` の並びを入れ替えると割り当てが変わった)。

## Decision

**tsconfig を実行環境ごとに `tsconfig.app.json`・`tsconfig.worker.json`・`tsconfig.node.json` の 3 つに分ける。ルートの `tsconfig.json` は `files: []`・`references`・`tsconfig.paths.json` への `extends` だけを持ち、3 つをつなぐ。共有する compiler の設定は `tsconfig.base.json` に、`paths` は `tsconfig.paths.json` に置く。どのファイルも 3 つのうち 1 つの `include` にだけ入れ、重なりは `tsconfig.app.json` の `exclude` で無くし、`references` の並び順に意味を持たせない (並び順で割り当てる案の却下の理由は案 A'')。**

| tsconfig               | 入れるファイル                                                                                                             | `lib`                                                                                                                                     | global の型                                                                                                                                      | `extends` の並び                                                   |
| ---------------------- | -------------------------------------------------------------------------------------------------------------------------- | ----------------------------------------------------------------------------------------------------------------------------------------- | ------------------------------------------------------------------------------------------------------------------------------------------------ | ------------------------------------------------------------------ |
| `tsconfig.app.json`    | `src/` と `pages/` の、`*.server.ts`・`*.server.tsx` 以外 (テストと story と `src/test/` を含む)、`.storybook/preview.tsx` | DOM あり                                                                                                                                  | `typeRoots` は `types/`、`types` は書かない。依存の型は `src/env.d.ts` の triple-slash (`vite-plus/client`・`vite-plus/test/browser-playwright`) | `tsconfig.base.json`、`.void/tsconfig.json`、`tsconfig.paths.json` |
| `tsconfig.worker.json` | 上の表の Cloudflare Workers の行と、Worker のディレクトリに置いたテスト。ディレクトリは `.ts` と `.tsx` の両方を入れる     | DOM なし                                                                                                                                  | `types` の `void/env`                                                                                                                            | `tsconfig.base.json`、`.void/tsconfig.json`、`tsconfig.paths.json` |
| `tsconfig.node.json`   | `scripts/`、`tooling/`、`vite.config.ts`、`void.config.ts`、`.storybook/main.ts`                                           | `lib` には DOM を書かない。依存の型から DOM が入る (`scripts/contrast/` が import する `colorjs.io` の型の `/// <reference lib="dom" />`) | `types` の `node`                                                                                                                                | `tsconfig.base.json` だけ                                          |

境界の判断:

- `pages/*.tsx` は、Worker の SSR でも動くが app に入れ、DOM の型で検査する。`src/components/` を描くのはブラウザが主で、DOM の型が要る
- worker の Workers の型は、Void の docs「Type Safety」の Setup どおり `types` の `void/env` から引く。Cloudflare の docs「Write Cloudflare Workers in TypeScript」は Worker の runtime の型に `wrangler types` の生成物を勧めるが、使わない。Void の公開の型は `@cloudflare/workers-types` を package の名前で参照し (Context)、Void の docs「AI」も model の名前と入力の型をこの package から引く。生成物を足しても、worker の program からこの package は外れない (Void 1.5.0)
- `src/` の `*.server.ts`・`*.server.tsx` は worker に入れる。app に入れると、Void の型を経た Workers の値 (`c.env.DB` など) の型が解決しない (Consequences)。`c.env.DB` を `string` に入れる誤りは型検査を通り、正しい `c.env.DB.prepare()` は `typescript/no-unsafe-*` で落ちた (2026-11-03)
- テストと story は、置いたディレクトリで tsconfig が決まる。`src/` と `pages/` のものは app、Worker のディレクトリのものは worker、`scripts/`・`tooling/` のものは node に入る。`*.server.ts` を試す `*.server.test.ts` も、`src/` と `pages/` に置けば app に入る (`exclude` の `**/*.server.ts` に当たらない)。tsconfig の区分は、ディレクトリと `*.server.ts`・`*.server.tsx` の接尾辞だけで決まり、付随ファイルの種別 (`scripts/lib/companion-files.ts`) を tsconfig に並べない
- unit のテストは Node で走るが、app のコードを読むので app に入れる。app は DOM の型も Node の型も持つ (Consequences)
- app の program は Workers の型を持たない (下の「Workers の型を app から外す」) ので、`src/` と `pages/` のテストに Workers の型の名前を書くと落ちる。`src/lib/` のテストに `D1Database` を書くと、`vp check` が TS2552 で落ちた (2026-11-03)
- `.void/tsconfig.json` は `void prepare` が書く。Void が生成する型 (`.void/routes.d.ts` など) の `files` と、その型へ向ける `paths` (`void/routes` など) を持つ。生成する型はブラウザのコード (typed fetch) と Worker のコードの両方が読むので、app と worker が継承する。node は Void の生成する型を読まない
- app と worker の `paths` は `tsconfig.paths.json` 1 つに置き、2 つが `extends` の最後に読む。2 つは自分の `paths` を書かない。TypeScript は `paths` を継承でマージせず、後に読んだ config の値で丸ごと置き換える (TSConfig Reference「extends」。マージを求める microsoft/TypeScript#44589 は 2026-11-02 時点で open)。自分の `paths` を書いた tsconfig では `.void/tsconfig.json` の `paths` が隠れる
- `tsconfig.paths.json` は `@/*` と、`.void/tsconfig.json` の `paths` の写しを持つ。写しのパスは `.void/` を前に付けてルートからの相対にする。Void の `void init --tsconfig` も、自分の `paths` を持つ tsconfig には `.void/tsconfig.json` の `paths` を写して合わせる (`packages/void/src/cli/init.ts` の `setupTsconfig`、1.4.0)
- worker も `@/*` を持つ。Vite の `resolve.tsconfigPaths` は、ファイルを `files` か `include` に持つ tsconfig の `paths` だけで解決する (Vite docs「resolve.tsconfigPaths」)。worker に `@/*` が無いと、`pages/x.server.ts` の `@/lib/…` の import が `vp check` で TS2307 になり、dev の SSR が 500 を返した (2026-11-02、Void 1.4.0)
- ルートの `tsconfig.json` は `tsconfig.paths.json` を `extends` し、`@/*` を 1 か所で持つ。shadcn の CLI はルートの `tsconfig.json` の `paths` しか読まない (shadcn-ui/ui#11466)。shadcn の docs「Installation > Vite」は、ルートと `tsconfig.app.json` の両方に同じ alias を書くよう案内している。ルートの `paths` を消して `shadcn add avatar --dry-run` を打つと、出力先が `@/components/ui/avatar.tsx` という字面のパスになった (2026-11-01、shadcn 4.22.2)。ルートが `tsconfig.paths.json` を `extends` する形では、同じ打ち方で出力先が `src/components/ui/avatar.tsx` になり、`shadcn info` の `importAlias` も `@` になった (2026-11-02、shadcn 4.22.2)。CLI は `extends` を辿って `paths` を読む
- 写しは `.void/tsconfig.json` の `paths` のうち、`void/db` と `void/routes` 以外を持つ
- `void/routes` は写さない。`.void/routes.d.ts` の `declare module "void/routes"` が `files` から効くので、写しが無くても型が付く。写すと、unit project (Node) で `void/routes` が `.d.ts` に解決し、`routeUrl()` が `TypeError: routeUrl is not a function` になった (2026-11-03、Void 1.5.0。1.5.0 から `void/routes` は実行時の値 `routeUrl` を export する)
- `void/db` は写さない。`void/db` を `.void/db.d.ts` へ向けると (`void/dist/db-types-*.mjs` の `generateDbDts` の docstring)、unit project (Node) で `void/db` が `.d.ts` に解決し、`TypeError: createDb is not a function` になった (2026-11-02、Void 1.4.0)。写さないと `db` の型は package の `void/dist/runtime/db.d.mts` の `DrizzleD1Database` (schema なし) になり、`db.query.*` の型は付かない。Vitest の中の `db` も schema と casing を持たないので、型と実行時は揃う

Workers の型を app から外す:

**app は `typeRoots` を `types/` にし、`types/@cloudflare/workers-types/index.d.ts` に中身の無い宣言を置く。** `void/env` などの `/// <reference types="@cloudflare/workers-types" />` は、`typeRoots` から先に探すので、app の program では空の宣言に解決する (`tsc --traceResolution` の primary search path で確かめた)。worker は `typeRoots` を書かず、Workers の型を読む。

- `typeRoots` を書いた program では、`compilerOptions.types` の名前を node_modules から探さない (`tsc --traceResolution` が "Resolving type reference directive for program that specifies custom typeRoots, skipping lookup in 'node_modules' folder." と出す。TypeScript 6.0.3)。そこで app は `types` を書かず、依存の global の型は `src/env.d.ts` の `/// <reference types="..." />` で足す。ファイルの中の triple-slash は、primary search path の `types/` に無ければ node_modules を探す (2026-11-03、`tsc --traceResolution` の "Looking up in 'node_modules' folder")。Vite の docs「Features」の Client Types は、`types` に書く形と、d.ts に triple-slash で書く形の両方を案内している
- `types` を書かなくても、`types/` の下は自動では読まれない。TypeScript 6.0 の既定の `types` は `[]` である (TypeScript 6.0 release notes「`types` now defaults to `[]`」)。空の宣言は、Void の型の triple-slash の参照からだけ program に入る (2026-11-03、`tsc --explainFiles`)
- `vitest/browser` の型 (playwright の provider が `cdp()` に足す `send` など) は、Vitest の docs「Assertion API」の TypeScript の tip どおり、tsconfig が覆うファイルに `/// <reference types>` を書いて読ませる。Vitest 4 からの、設定のファイルで provider を import すれば reference が要らない形 (Vitest blog「Vitest 4.0 is out!」) は、設定のファイルとテストが同じ program にあるときに効く。provider を import する `tooling/test/` の設定は node の program にあるので、app には届かない。`src/env.d.ts` の参照を消すと、`cdp().send` の TS2339 が 4 件出た (2026-11-24、Vitest 5.1.0、vite-plus 1.7.0 の tsrs 7.1.0-beta.tsrs2)。`vite-plus/test/browser-playwright` は `@vitest/browser-playwright` の再 export である (Vite+ docs「Migrate to Vite+」)
- `void/env` などは、Void の docs のとおりの場所で import してよい。`env.ts`、`pages/**/*.server.ts`、`routes/`、`middleware/`、`src/**/*.server.ts` のどれでも、app の型検査は落ちない (下の実測)。client のコードから読める値は ADR-0055 の Context の表の `void/env` の行が持つ

| probe なし、F                                            | 通る                                                                                                      |
| probe あり、F                                            | DOM の `append` の TS2345 は 0 件。残ったのは probe の書き方による lint (`no-base-to-string`) の 1 件だけ |
| probe あり、app に `typeRoots` を書かない                | TS2345 が 9 件で落ちる                                                                                    |
| probe あり、`typeRoots` は書き、空の宣言のファイルを消す | TS2345 が 9 件で落ちる                                                                                    |

F で、`src/lib/` に `new HTMLRewriter()` と `D1Database` を書くと、`vp check` は TS2304 と TS2552 で落ちた。`middleware/` と `src/lib/` の `*.server.ts` に `document` を書くと、`vp check` は TS2584 で落ちた (2026-11-03)。

`paths` の置き場所:

| 案                                                                                                             | 評価                                                                                                                                                                        | 採否     |
| -------------------------------------------------------------------------------------------------------------- | --------------------------------------------------------------------------------------------------------------------------------------------------------------------------- | -------- |
| P. `tsconfig.paths.json` に `@/*` と `.void/tsconfig.json` の `paths` の写しを置き、app と worker が最後に読む | 写しの置き場所が 1 つで済む。node の `extends` は変わらない                                                                                                                 | **採用** |

U の実測 (2026-11-02、TypeScript 6.0.3、Vite 8.3.5。Vite は vite-plus-core 1.4.0 に同梱で、build API を client と ssr で走らせた):

| `imports` の形                                    | specifier              | tsc    | Vite                                                  |
| ------------------------------------------------- | ---------------------- | ------ | ----------------------------------------------------- |
| `"#/*": "./src/*"`                                | 拡張子なし             | TS2307 | 通る                                                  |
| `"#/*": "./src/*"`                                | 拡張子つき             | 通る   | 通る                                                  |
| `"#/*": ["./src/*.ts", "./src/*.tsx", "./src/*"]` | 拡張子なし             | 通る   | `.tsx` を指す側で "Rolldown failed to resolve import" |
| shadcn の docs の形 (`#components/*` → `*.tsx`)   | `components/` の `.ts` | TS2307 | 解決に失敗                                            |

- `src/components/` には `.ts` と `.tsx` が混ざる (`src/components/parts/data-table-columns.ts` など) ので、拡張子を書かない限り成り立たない
- 公式は `#/` の subpath imports を支持している。TypeScript 6.0 の release notes「Subpath Imports Starting with `#/`」は "TypeScript now supports it under the options `nodenext` and `bundler`" と書き、shadcn の changelog「May 2026 - Package Imports and Target Aliases」は `shadcn@4.7.0` からの対応とする
- 拡張子を書く形の代償は、`@/` の全置換、lint の正規表現 (`tooling/lint/config.ts` の `^@/components/`・`@/test/`) の書き換え、`components.json` と `docs/registry-baseline/` の作り直し、upstream からの cherry-pick の衝突である

型検査の実行:

**型検査は `vp check` だけで見る。tsrs の README が勧める別の `tsrs --noEmit` は走らせない。** Vite+ docs「Check」(v1.7.0) は "We recommend turning both `typeAware` and `typeCheck` on so `vp check` becomes the single command for static checks during development." と書く。

- 型検査の範囲は lint の対象と同じで、lint の対象から外したファイルと宣言ファイルは型検査されない (tsrs の `README.md`「Type-aware lint」: "Files Oxlint does not lint are not type-checked, so keep a separate `tsrs --noEmit` run to check whole tsconfig programs."、oxc-project/tsrs#998)。範囲は tsgolint のときから同じで、vite-plus は oxc-project/tsrs#998 の入った tsrs 7.1.0-beta.tsrs2 で tsgolint を置き換えた (voidzero-dev/vite-plus#3352)
- 今は差が出ない (2026-11-24)。`tooling/lint/config.ts` の `ignorePatterns` が外す TS のファイルは `docs/registry-baseline/` の baseline だけで、どの tsconfig の `include` にも入らない。宣言ファイル (`src/env.d.ts`、`types/` の空の宣言、`.void/` の生成物) は、`tsconfig.base.json` の `skipLibCheck: true` で `tsc` も検査しない。確かめ方は、`git ls-files -co --exclude-standard` の TS のファイルを `ignorePatterns` と突き合わせることと、`src/` に置いた `.d.ts` の型の誤りを `vp check` と `vp dlx -p typescript@6.0.3 tsc -p tsconfig.app.json --noEmit` がどちらも通すのを見ること
- 位置の無い global の診断は、tsrs 7.1.0-beta.tsrs2 の lint の型検査では報告されない (tsrs の `tools/tsgolint/README.md`: "Global diagnostics without a source location, such as missing global types, are not reported.")。oxc-project/tsrs#1068 (2026-11-22 に merge、2026-11-24 時点でどの tag にも無い) は、program ごとに tsconfig の上で報告すると docs を書き換えた。tsconfig の `types` の誤りは、この経路ではなく tsconfig を読む段の `typescript(tsconfig-error)` で落ちる (Consequences)
- 黙って見逃す既知の経路がある。同じ名前の `.ts` と `.tsx` が並ぶと、lint の型検査がそのファイルを tsconfig から外して推論した program で検査し、tsconfig の `compilerOptions` を落として型の誤りを見逃す。`tsrs --noEmit` は拾う (oxc-project/tsrs#1046、2026-11-24 に open)。2026-11-24 に `git ls-files '*.ts' '*.tsx' | sed -E 's/\.tsx?$//' | sort | uniq -d` は何も出さなかった
- 別に型検査を走らせるのは、tsconfig の `include` に入る TS のファイルを lint の対象から外すとき (生成した TS を `ignorePatterns` に足すなど) と、同じ名前の `.ts` と `.tsx` を並べるときである。Vite+ docs (v1.7.0) は同梱の tsrs を打つ形を案内せず、`vp exec tsrs` は `Command 'tsrs' not found in node_modules/.bin` で落ちる。2026-11-24 に `vp dlx -p tsrs@<版> tsrs -b` (版は `vp --version` の `tsrs` の行) は、誤りの無いツリーで exit 0、`src/lib/` に置いた TS2322 で exit 2 だった

## Consequences

- `vp check` は 3 つの tsconfig をすべて検査する。2026-11-24 に、範囲ごとにわざと誤りを入れて確かめた (vite-plus 1.7.0 の tsrs 7.1.0-beta.tsrs2、Void 1.11.0)

  | 誤りを入れたファイル (program)                        | `document`                                                                                                    | `process.env.HOME` を `string \| undefined` に | `Buffer.from("a")` を `number` に                           | `D1Database`    | `HTMLRewriter`  |
  | ----------------------------------------------------- | ------------------------------------------------------------------------------------------------------------- | ---------------------------------------------- | ----------------------------------------------------------- | --------------- | --------------- |
  | `middleware/` と `src/lib/` の `*.server.ts` (worker) | TS2584 で落ちる                                                                                               | 通る (型は `string \| undefined`)              | `any` になり、TS は通る (`typescript/no-unsafe-*` が落とす) | 通る            | 打っていない    |
  | `src/lib/` (app)                                      | 型が付く (`number` に入れると TS2322)                                                                         | 通る                                           | TS2322。`Buffer` に Node の型が付く                         | TS2552 で落ちる | TS2304 で落ちる |
  | `src/lib/` のテスト (app)                             | 型が付く                                                                                                      | 打っていない                                   | TS2322                                                      | TS2552 で落ちる | 打っていない    |
  | `scripts/` (node)                                     | 型が付く (`number` に入れると TS2322)。DOM の型が `colorjs.io` の型から入るので、node は DOM の誤りを止めない | 打っていない                                   | TS2322                                                      | TS2552 で落ちる | 打っていない    |

- worker は DOM の global を止め、app は Workers の global を止める。app は Node の global (`process`・`Buffer`) を止めず、node は DOM の global を止めない
- 3 つの tsconfig の `include` から決まる根のファイルは重ならない。`.void/tsconfig.json` から受け継ぐ `files` (`.void/routes.d.ts` など) は、app と worker の両方に入る。Void の生成する型は両方が読む (Decision の `.void/tsconfig.json` の項)。app か worker が `files` を書いてこの重なりを無くすと、その tsconfig から Void の生成する型が外れる。`tsconfig.app.json` の `exclude` の `*.server.ts`・`*.server.tsx` は、`tsconfig.worker.json` の `include` と字面で揃える。ずれると、そのファイルはどの tsconfig にも入らず推論した program で検査されるか、2 つの tsconfig に入る。`vp check` は重なりも漏れも知らせない。確かめる手順は `docs/guides/placement.md`「tsconfig にファイルを割り当てる」にある
- どの tsconfig の `include` にも入らないファイルも、`vp check` は既定の設定の program で検査する (tsrs の `tools/tsgolint/README.md`「Type checking in the lint run」: "Listed files outside every tsconfig are linted and type-checked in an inferred program with the linter's default compiler options.")。`lib`・`types`・`paths` は 3 つのどれとも違うので、置き場所の実行環境に合った誤りは出ない。2026-11-24 に、どこにも入らない `misc/x.ts` で、`document.title` を `number` に入れると TS2322 (DOM の型が付く)、`process.env.HOME` は TS2591、`@/lib/app-name` の import は TS2307 で落ちた (vite-plus 1.7.0 の tsrs 7.1.0-beta.tsrs2)。ルートに新しいディレクトリやファイルを置いたら、どれかの `include` に足す
- ページの型は Void の docs「Type Safety」どおり、`.server.ts` の `export type Props = InferProps<typeof loader>` をページが `import type` で受ける。受けた `.server.ts` は app の program に入るが、F によって Workers の型は足されない
- server のファイルは、Context の経路で app の program にも入る。そこでは Workers の型の名前が解決しない。名前を直に書くと `tsc -p tsconfig.app.json` は TS2552 を出す。Void の型を経た値は、型が解決しないまま通る。`c.env.DB` の型は `void/dist/env-public-*.d.mts` の `Cloudflare.Env` が参照する `D1Database` で、その解決の誤りを `tsconfig.base.json` の `skipLibCheck: true` が隠す
- `vp check` (tsrs) は、ファイルを `include` に持つ tsconfig の program で検査し、import で別の program に入っただけのファイルはその program では検査しない (tsrs の `tools/tsgolint/README.md`「Type checking in the lint run」: "the program's other files supply types without their own diagnostics being reported")。server のファイルは worker の program で Workers の型が付く。app のファイルから import した `src/lib/` の `*.server.ts` で `D1Database` の値を `string` に入れると、`vp check` は TS2322 で落ちた。逆に、worker のファイルが import する app のファイルは app の program で検査される。`middleware/` から import した `src/lib/` のファイルが `document` を使っても、`vp check` は通った (2026-11-24、vite-plus 1.7.0 の tsrs 7.1.0-beta.tsrs2)。`tsc` は program ごとに import の先まで検査する。ページの import から app に入る `src/lib/` の `*.server.ts` で `c.env.DB` を `string` に入れても `tsc -p tsconfig.app.json` は通り、worker のファイルが import する app のファイルの `document` は `tsc -p tsconfig.worker.json` だけが TS2584 で落とした (2026-11-03、`pages/<path>.server.ts`・`src/lib/` の `*.server.ts`・`middleware/` から import した形)。型検査の合否は `vp check` で見る (Decision「型検査の実行」)。`vp check` は program を選べず、`typescript` は直接の依存に無いので `vp exec tsc` は動かない。program を指定した `tsc` は `vp dlx -p typescript@6.0.3 tsc -p tsconfig.worker.json --noEmit` と打ち、`--explainFiles` と `--traceResolution` で経路を調べるときに使う (この文書の `tsc` はこの打ち方。6.0.3 は実測した版。2026-11-03 に `--noEmit` と `--showConfig` が動くことを確かめた)
- `src/` と `pages/` のテストは app の program で検査されるので、テストの中の `c.env.DB` は型が解決しない。テストのファイルでは `typescript/no-unsafe-*` の多くを外している (`docs/guides/lint/configuration.md`「テストファイルの緩和」) ので、`src/lib/` のテストで `c.env.DB` を `string` に入れても `vp check` は通った (2026-11-03)
- app の program に global の型を足すときは、`src/env.d.ts` に `/// <reference types="..." />` を足す。tsconfig の `types` に足した名前は node_modules を探さないので、どのファイルも参照していない名前は TS2688 で落ちる。ほかのファイルの triple-slash が解決する名前は、`types` に書いても通る (2026-11-04、`tsc --types`、TypeScript 6.0.3)。`vp check` では、参照されていない名前は TS2688 ではなく、type-aware lint の tsrs-lint が tsconfig を読む段の `typescript(tsconfig-error)` ("Invalid tsconfig"、help は "Cannot find type definition file for '<名前>'.") で落ちる。型検査の診断ではなく、`typeCheck` を切っても出て、`typeAware` を切ると出ない (2026-11-24、vite-plus 1.7.0 の tsrs 7.1.0-beta.tsrs2)
- `.void/db.d.ts` も先頭に `/// <reference types="@cloudflare/workers-types" />` を持つ。app では、この参照も空の宣言に解決する (2026-11-03、`tsc --traceResolution`)
- app の program は Node の型を持つ。経路は次の 3 つである (2026-11-04、`tsc --explainFiles`)
  - `src/env.d.ts` の `vite-plus/test/browser-playwright` が `vitest/node` を経て `vite/node` の型を読み、`/// <reference types="node" />` に届く。どのページがあっても無くても入る。`src/env.d.ts` と `Buffer` を使う 1 ファイルだけの program でも `Buffer` に型が付き、`src/env.d.ts` を外すと TS2591 で落ちた。テストと story が import する Vitest と Storybook の型も、同じく `vite/node` を読む
  - `@void/react` の型は `void` を import する。`Link` や `useRouter` を import するファイル (layout やリンクの部品など) が app に入ると、`void/dist/index.d.mts` が `vite/node` の型を読み、`/// <reference types="node" />` に届く。`src/env.d.ts` を含めず、`Link` を import するファイル 1 つだけの program でも `Buffer` に型が付き (TS2322)、その import を外すと TS2591 で落ちた (2026-11-04)。`@void/react` を import するファイルが 1 つも無ければ、この経路は無い
  - Context の経路で app に入る server のファイル (loader か action を持つ `pages/<path>.server.ts` など) が `void` を import すると、同じ `void/dist/index.d.mts` が `vite/node` と `@cloudflare/vite-plugin` (→ `miniflare` → `undici`) の型を読み、`/// <reference types="node" />` に届く。そういうファイルが 1 つも無ければ、この経路は無い
- Void が `.void/tsconfig.json` に `paths` を足しても、`tsconfig.paths.json` に写すまで app と worker からは見えない。2026-11-02 に `.void/tsconfig.json` へ別名を 1 つ足すと、それを import する `src/lib/` と `routes/` のファイルが TS2307 で落ち、`tsconfig.paths.json` に写すと通った。Void 1.4.0 が足す別名は、DB を使うと `void/db`・`@schema`・`@schema/*`、`queues/` を置くと `void/queues`、`.void/md.d.ts` ができると `@void/md/pages` である (`packages/void/src/codegen/project-tsconfig.ts` の `createProjectTsconfig`)。`.void/tsconfig.json` の `paths` と `tsconfig.paths.json` の写しは、`vp dlx -p typescript@6.0.3 tsc -p tsconfig.worker.json --showConfig` の `paths` から `@/*` を除いた組と、`.void/tsconfig.json` の `paths` から `void/db` と `void/routes` を除き、`./` で始まる値の前に `.void/` を付けた組 (`./queues.d.ts` → `./.void/queues.d.ts`) を比べて突き合わせる。`@schema` と `@schema/*` は `.void/tsconfig.json` では `../db/schema.ts` の形で、ルートからの相対 (`./db/schema.ts`) に直して比べる。2026-11-03 にこの手順を打つと、どちらも `@schema`・`@schema/*` の 2 組で一致した (Void 1.5.0)
- `void init --tsconfig` は、ルートの `tsconfig.json` に `extends: "./.void/tsconfig.json"` と `types: ["void/env"]` を足し、コメントを消す。打ち直したら、ルートの変更を戻し、必要な変更を 3 つの tsconfig と `tsconfig.paths.json` へ手で写す
- 型の program が増えた分だけ `vp check` の時間が延びる余地がある。3 つに分けた状態で、`vp check` の lint と型検査は 2.7 秒だった (2026-11-03、386 ファイル)
