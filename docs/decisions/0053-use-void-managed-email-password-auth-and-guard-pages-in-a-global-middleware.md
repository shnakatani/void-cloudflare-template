# ADR-0053: 認証は Void が管理する email とパスワードに限り、ページの保護は global の middleware で行う

- Status: Accepted
- Date: 2026-11-03
- 関連: ADR-0016 (`usePageAction` の失敗の通知)、ADR-0047 (`CloudContextVariables` の augmentation は worker の program にだけある)、ADR-0048 (テストで `SharedContext` に値を渡す)、ADR-0052 (auth の table の migration)、ADR-0054 (保護を preview で確かめる)、ADR-0060 (別の origin からの書き込みと、`routes/` の handler で user を読む)

## Context

Void は Better Auth を管理して持つ。`void/auth` から import するか、`void/client` から `auth` を import すると有効になる (Void の docs「Authentication」の Config)。

| 項目                  | 中身                                                                                                                                                                                                                                                                                                                                                                                                                   |
| --------------------- | ---------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------- |
| 既定の provider       | email とパスワードだけ (Void の docs「Authentication」の Config)。2026-11-02 時点 (Void 1.4.0 の `runtime/better-auth-shared.ts` の `resolveEmailAndPassword`) の記録では、Void は Better Auth の `emailAndPassword` に `enabled` とパスワードの hash の関数だけを渡し、確認メール (`requireEmailVerification`・`emailVerification.sendVerificationEmail`) とパスワードの再設定 (`sendResetPassword`) は既定に無かった |
| 設定を足す口          | ルートの `auth.ts` の `defineAuth(({ defaults }) => ({ ...defaults, … }))`。deep merge しない (Void の docs「Authentication」の Customization)                                                                                                                                                                                                                                                                         |
| server で user を読む | `void/auth` の `getUser()` (`AuthUser \| null`) と `requireAuth(c)`。`requireAuth(c)` は user が無ければ 401 を throw し、`requireAuth(c, { throwRedirect: <URL> })` は login などへの redirect を throw する (GET・HEAD は 302、ほかの method は 303。Void の docs「Auth API」の `requireAuth(c, options?)`)                                                                                                          |
| client からの操作     | `void/client` の `auth` (Better Auth の client、`/api/auth`) の `signUp.email`・`signIn.email`・`signOut`。server からは `getAuth(c).api` で Better Auth の API を呼べ、`signInEmail`・`signUpEmail` は今のブラウザをサインインさせる (Void の docs「Auth API」の `getAuth(c)`)                                                                                                                                        |
| 全ページへの値        | middleware で `c.set("shared", …)` し、画面は `useShared()` で読む (Void の docs「Layouts & Shared Data」の Shared Data)。Void 1.7.0 から、shared data の `Date` は browser でも `Date` のまま届く (Void の docs「Loaders」)                                                                                                                                                                                           |
| secret                | dev は secret の設定が要らず、`vp preview` には `BETTER_AUTH_SECRET` が要り、deploy は無ければ作る (Void の docs「Authentication」の Behavior)。2026-11-02 時点 (Void 1.4.0 の `runtime/better-auth-shared.ts`) の記録では、dev は `BETTER_AUTH_SECRET` が無ければ固定値に倒れ、dev 以外 (`vp preview` を含む) は要求ごとに `auth: Missing Better Auth secret` で throw していた                                       |
| rate limit            | deploy 先の Cloudflare では、Better Auth の既定で client の IP ごとに効く (サインインは 10 秒に 3 回など)。数は Worker の instance ごとに持つ ("Each Worker instance keeps its own count.")。instance をまたいで 1 つに数えるには `rateLimit: { storage: 'database' }` にし、direct の Cloudflare では `void db generate` を打つ。dev では効かない (Void の docs「Authentication」の Behavior)                         |

ページを守る場所の候補は、Void の docs (「Server Routing」の Global middleware と Per-route middleware、「Not Found & Errors」の HTTP exceptions、「Auth API」の `requireAuth(c, options?)`) のとおり次のように振る舞う。このテンプレートは `pages/` に `_error` を持たない (ADR-0050)。

| 守る場所                                                                           | 振る舞い                                                                                                                                                                                                                                                                                                                                                                                                                      |
| ---------------------------------------------------------------------------------- | ----------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------- |
| global の middleware (`middleware/NN.<name>.ts`)                                   | すべての要求に掛かり、page の loader と action の前に走るので、`getUser()` が読める                                                                                                                                                                                                                                                                                                                                           |
| page の loader・action に middleware を渡す (`defineHandler(middleware, handler)`) | 渡せる。page の `GET`・`HEAD` の要求では、loader より前の middleware が throw すると、loader を飛ばして root の error component を出し、無ければ例外の応答を返す。action の要求は error component を通らず、action の失敗の扱いになる (Void の docs「Not Found & Errors」の HTTP exceptions: "Error components handle these exceptions on page GET and HEAD requests. API routes and actions keep their own error handling.") |
| page の loader で `requireAuth(c)`                                                 | `throwRedirect` を渡せば login へ送る。渡さなければ 401 で、近い `_error` が描き、無ければ例外の応答になる                                                                                                                                                                                                                                                                                                                    |
| loader ごとに `getUser()` を見て redirect する                                     | 動くが、守るページの loader ごとに書くことになる                                                                                                                                                                                                                                                                                                                                                                              |

2026-11-23 時点 (Void 1.11.0 の `packages/void/src/pages/client.ts`) の記録では、action の要求を redirect すると、Void の client は redirect を辿った先のページを action の成功として受け取っていた。`submitAction` は `router.visit` が redirect の行き先の GET で決着すれば `ok: true` を返していた。`requireAuth(c, { throwRedirect })` を action で使っても redirect なので、同じ扱いになる作りだった。2026-11-03 に Void 1.4.0 の `vp preview` で、action を持つ守るページのダイアログから、session の cookie を消して送ると、action の `POST` が 302、`GET /login` が 200 で、書き込んでいないのに `onSuccess` の完了の文言が読み上げられ、入力がダイアログごと消えた。action の要求に 401 を返すと、client は 401 を throw する (Void の docs「Actions & Forms」の Validation Errors)。middleware は `next()` を呼ばずに応答を返して要求を止められる (Void の docs「Server Routing」の Per-route middleware: "Each can short-circuit (return a response without calling `next()`)"。同じ docs の Global middleware は、`basicAuth()` で要求を止める gate を global に置く例を書く)。`requireAuth(c)` は 401 の `HTTPException` を throw する (Void の docs「Auth API」)。

別の origin から資格情報つきで送る要求のうち、simple request でないものの前に、ブラウザは CORS の preflight (`OPTIONS`) を送る。preflight は資格情報を付けずに送られる (Fetch Standard の「HTTP responses」: "For a CORS-preflight request, request's credentials mode is always "same-origin", i.e., it excludes credentials")。応答が ok status (200-299) でなければ preflight は失敗し、本来の要求は送られない (Fetch Standard の「CORS-preflight fetch」)。2026-11-03 時点 (Hono 4.13.14 の `src/middleware/cors/index.ts`) の記録では、Hono の `cors` は `OPTIONS` の要求に `next()` を呼ばずに 204 を返していた。Void の docs は `cors` を global の middleware (`middleware/01.cors.ts`) に置く例 (docs「Hono」の Built-in Middleware) と、route の handler に渡す例 (docs「Server Routing」の Per-route middleware) を書く。2026-11-03 時点 (Void 1.5.0 の `dist/index.mjs` の route を張る処理) の記録では、route のファイルは `OPTIONS` も export でき、method を export したファイルは export した method の要求だけを受けていた。method を 1 つも export しないファイルは、default export がすべての method を受けていた。

middleware の `c.redirect()` は、渡した location に要求の query を足さない (Void の docs「Redirects」: "It sends the location you provide without adding the request query.")。それでも middleware の redirect を絶対 URL で渡すのは、すべての `c.redirect` を 1 つの規範にそろえるためである。named action の相対の redirect は action の URL に書いた query を行き先に残すので、保存のあとの redirect には絶対 URL が要る (ADR-0056)。相対の path に替えるなら、`location` を絶対 URL で比べる `verify:auth-redirect` も直すことになる。

## Decision

**認証は Void が管理する Better Auth の既定 (email とパスワード) だけで組む。ページの保護と全ページへの user は `middleware/01.auth.ts` の global の middleware に置く。middleware が redirect するのは画面を開く要求 (`GET`・`HEAD`) だけにし、`OPTIONS` (CORS の preflight を含む) は通し、守る path へのそれ以外の method の未ログインの要求は、middleware が 401 で止める。**

- 確認メールとパスワードの再設定は入れない。足すときはルートの `auth.ts` に書く (`docs/guides/auth.md`「確認メールとパスワードの再設定を足す」)
- middleware は `src/features/auth/access.ts` の `pathAccess` で path を 3 つに分け、`authGuard` が返す扱い (`redirect`・`unauthorized`・`pass`) に従う。redirect は絶対 URL で送り、401 は `HTTPException(401, { message: "Unauthorized" })` を投げて `requireAuth(c)` と同じ応答にする
- 守るページの loader と action も `requireAuth(c)` で user を読む。未ログインの action の 401 は、`usePageAction` の toast がログインし直しを案内する (ADR-0016)

| 区分                               | 未ログイン                                                               | ログイン済み                                      |
| ---------------------------------- | ------------------------------------------------------------------------ | ------------------------------------------------- |
| `protected` (`PROTECTED_PATHS`)    | `GET`・`HEAD` は `/login` へ。`OPTIONS` はそのまま。ほかの method は 401 | そのまま                                          |
| `guest-only` (`/login`・`/signup`) | そのまま                                                                 | `GET`・`HEAD` は `/` へ。ほかの method はそのまま |
| `public` (どちらにも無い path)     | そのまま                                                                 | そのまま                                          |

- middleware は `shared` に `{ auth: { user } }` を入れる。`user` は `AuthUser` を詰め替えた `SharedUser` (`id`・`email`・`name`) か `null` で、型は `src/features/auth/shared.ts` が持つ
- 画面は `useShared<AppShared>()` で読む。augmentation は worker の program にだけあるので、型引数で渡す (ADR-0047)
- ログイン・登録・ログアウトは、画面から client の `auth` を呼ぶ。成功したら遷移を始める (`docs/guides/auth.md`「Better Auth の client から送る」)

## Consequences

- 保護する path は `src/features/auth/access.ts` の `PROTECTED_PATHS` に足す。どちらの一覧にも無い path は `public` で、未ログインでも開く (fail-open)。足し忘れても何も落ちないので、守る path ごとに `scripts/checks/runtime/auth-redirect.ts` の期待値に 1 行足す
- 一覧に無い path の handler では、`requireAuth(c)` だけが未ログインの要求を止める。handler が `getUser()` で読んで `null` のまま書くと、未ログインの要求が書き込みまで届く
- 守る path への、`trustedOrigins` に無い別の origin からの書き込みの要求は、Void の page の action の origin の判定 (403、ADR-0060) より先に、middleware の 401 で止まる。別の origin からの `POST` などは、その origin が `trustedOrigins` に無ければログインした session を使わない (Void の docs「Authentication」の Behavior) ので、cookie を付けて送っても 401 になる。2026-11-03 に Void 1.4.0 の `vp preview` で測ったときも 401 だった。`trustedOrigins` の origin からログインした cookie を付けて送ると、session が使われて middleware を通り、page の action の 403 になる (Void の docs「Actions & Forms」の Authentication and origin checks: "Void rejects cross-origin page actions with `403 Forbidden`.")
- middleware は守る path でも `OPTIONS` を止めない。route の handler が `OPTIONS` を受けるなら (`export const OPTIONS`、または method を export しない default export)、preflight に答えるだけにし、書き込まない
- 守るページを prerender しない。`.md` のページと、loader の無い island のページは自動で prerender されるので (Void の docs「Edge Prerendering」)、守る path の下に置かない。2026-11-03 時点 (Void 1.5.0 の `dist/prerender-render-*.mjs`) の記録では、prerender は build の時点の HTML と page data (`/_void/pages/<path>.json`) を静的な出力に書いていた。その配信が middleware の判定を通るかは確かめていない
- 2026-11-02 時点 (`@void/react` 1.4.0 の `runtime/pages-client.ts`) の記録では、`SharedContext` には page data の `shared ?? {}` が入っていた。`pages/layout.tsx` は描画の先頭で `.auth` を分割代入するので、middleware を通らずに描かれたページでは layout が throw する。layout の中の `AppErrorBoundary` はまだ mount されていないので、この throw を受ける境界は無い。いまは middleware がすべての要求で `shared` を入れる
- `vp preview` と deploy には `BETTER_AUTH_SECRET` が要る。preview への渡し方は `docs/guides/auth.md`「preview に secret を渡す」
- deploy 先では IP ごとの rate limit が効く。deploy したアプリへ何度も sign up する end-to-end のテストは、この制限に当たる
- rate limit の数は Better Auth の既定のまま instance ごとの memory に持ち、instance の間で共有しない。1 つの IP からの要求が複数の instance に散ると、instance の数だけ上限が緩む。共有するときは、ルートの `auth.ts` で `rateLimit: { storage: 'database' }` にし、`vp exec void db generate` で生成した migration を commit する (Void の docs「Authentication」の Behavior、`docs/guides/database.md`「auth の設定を変える」)。Better Auth は数を DB の `rateLimit` の table に持つので (Better Auth の docs「Rate Limit」)、auth の要求ごとに D1 を読み書きすることになる (推論)
- サインインした要求への応答には `Cache-Control: no-store` が付く (Void の docs「Authentication」の Behavior)
- 登録で `USER_ALREADY_EXISTS` を欄のエラーに出すので、登録済みの email を第三者が調べられる (Better Auth の既定)。`requireEmailVerification` か `autoSignIn: false` にすると、登録済みの email にも同じ応答を返して調べられなくなる
- Better Auth の `requireEmailVerification` か `autoSignIn: false` を `auth.ts` で設定すると、登録の成功で session が作られず、登録済みの email にも成功を返すようになる。登録の画面と文言を合わせて直す (`docs/guides/auth.md`「auth の設定を変える」)
