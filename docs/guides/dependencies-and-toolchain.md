# 依存と開発環境

依存を足す・上げる・前倒しするとき、ツールや設定を足すとき、commit hook を止めるときの手順と落とし穴を持つ。

| 決定                                                                                        | ADR      |
| ------------------------------------------------------------------------------------------- | -------- |
| 開発環境のツールチェーンは mise と Vite+ に寄せる                                           | ADR-0004 |
| 依存更新は待機 3 日で統一し、pin には出口条件を書く                                         | ADR-0005 |
| GitHub Actions の定義は zizmor で検査し、action は workflow の lockfile で固定する          | ADR-0006 |
| テストの import を重くする依存のバレルは使わず、個別エントリポイントから引き、lint で止める | ADR-0032 |

## how-to

### 手元の環境を用意する

- mise のシェル hook を入れる。`[env]` の値は、hook が読み込んだシェルか `mise x --` から打った `vp run` のタスクに届く。hook が走らないシェル (エージェントのシェル、hook の無い IDE のタスク) では、それを読むタスクが未設定で止まる (ADR-0004)
- dev server と Storybook は `mise run serve` と `mise run storybook` で起動する。mise のタスクが worktree ごとの port を渡すので、hook の無いシェルからも同じ port で起動する。hook を読んだシェルで `vp run serve` を直に打つと、worktree の中でも既定の port で起動する (ADR-0004)。エージェントのシェルでは「dev server と Storybook を止める」のとおり `mise daemons start` で起動する
- mise は `.mise.toml` の `min_version` 以上にする。古い mise は設定の読み込みで止まる (ADR-0004)
- 素の `pnpm` は corepack などで別に入れない。Vite+ の shim が `packageManager` の版の `pnpm` を用意する ([Vite+ docs「Environment」][]。確かめた結果は「入口を `vp` にそろえる理由」)
- Node.js と pnpm 以外のツールを足すときは、`.mise.toml` の `[tools]` へ宣言する。手元でグローバルに入れたものに依存しない

### dev server と Storybook を止める

- 前面で起動した `mise run serve` と `mise run storybook` は、端末の Ctrl-C で止める。Ctrl-C は前面のプロセスグループ全体に SIGINT を送る
- background で動かすときは `&` ではなく `mise daemons start serve` (Storybook は `storybook`) で起動し、`mise daemons stop <同じ名前>` で止める。`mise daemons stop` は port を持つ子孫まで止める (ADR-0004)
- 起動したプロセスの pid にだけ SIGTERM を送らない。2026-10-14 に mise 2026.10.3、vite-plus 1.1.0 で、`mise run serve` の pid にだけ SIGTERM を送ると、mise は終わったが、port を持つ子孫の vite の node が残った。残ったサーバーが worktree の port を持ち続けると、次の `mise run serve` は別の port へずれずに終わる (使用中の port で終わらせる理由は ADR-0004)

### 依存を足したページの最初の要求が dev で 500 になったら

dev の事前バンドルのキャッシュ (`node_modules/.vite`) を作ったあとに、まだ使っていなかった依存を import するページを足すと、そのページの最初の要求で Vite が依存を事前バンドルし直し、worker を読み直す ([Vite docs「Dependency Pre-Bundling」][] の Automatic Dependency Discovery)。その要求は `TypeError: Cannot read properties of null (reading 'useContext')` で 500 になる。

- もう一度読み込む。事前バンドルし直したあとの要求は通る
- `optimizeDeps.include` に足さない。page から辿れる import は、キャッシュの無い起動で Void の設定 (worker の環境の `entries` が `pages/**`) が拾う。`include` は、plugin の変換で生まれる import のように走査で見つからない依存のためのもの ([Vite docs「Dependency Pre-Bundling」][] の Customizing the Behavior)
- キャッシュを作り直すなら、dev server を止めてから `node_modules/.vite` を消す。キャッシュは lockfile や `vite.config.ts` が変わるまで作り直されない ([Vite docs「Dependency Pre-Bundling」][] の Caching)

2026-11-02 に Void 1.4.0、vite-plus 1.4.0 (Vite 8.3.5) で、`@tanstack/react-table` と `@base-ui/react/alert-dialog` を初めて import するページを足したあとの最初の要求が 500 になり、2 回目は 200 だった。キャッシュの無い起動では、同じページの最初の要求が 200 だった。

### commit hook を扱う

commit のたびに、`vp staged` が `vite.config.ts` の `staged` のコマンドを staged のファイルへ当てる。`vp staged` は `.vite-hooks/pre-commit` から呼び、hook のディスパッチャ (`.vite-hooks/_`) は `package.json` の `prepare` の `vp config` が入れる ([Vite+ docs「Commit Hooks」][])。

- `vp staged` と hook の間に、自前の skip のスクリプトを挟まない。止める手段は、Vite+ が入れた hook 自身が実行のたびに確かめる ([Vite+ docs「Commit Hooks」][]: "The installed hooks check the environment on every run, so you can disable them per machine or per process without uninstalling anything.")
- hook を止めるときは、止める範囲で [Vite+ docs「Commit Hooks」][] の手段を選ぶ。CI のビルドコンテナのように環境ごと止めるなら `VP_GIT_HOOKS=0` を設定する。`prepare` の `vp config` が hook を入れず、入っている hook も何もせずに終わる (Environment variable の節)。コミットするプロセスがシェルの環境を受け継がない (デーモンなど) なら、マシンごとの init script (`$XDG_CONFIG_HOME/vite-plus/hooks-init.sh`。既定は `~/.config/vite-plus/hooks-init.sh`) で `VP_GIT_HOOKS=0` を export する (Init script の節)。1 つの clone で止めるなら `vp hooks disable` を打つ (Removing commit hooks の節)
- `staged` のコマンドに付けた `--no-error-on-unmatched-pattern` を外さない。staged のファイルが `ignorePatterns` に当たるもの (`.claude/skills/**` の中のファイルなど) だけのコミットでは対象が 0 件になり、このフラグが無いと `vp fmt` と `vp lint` が error で終わって commit が止まる (`vp fmt --help` と `vp lint --help` のこのフラグの説明)。2026-10-06 に vite-plus 1.0.0 で、`ignorePatterns` に当たるファイルだけを渡すと、フラグの無い `vp fmt --write` は exit 2 (`Expected at least one target file`)、`vp lint` は exit 1 で終わった

### 依存を足す・外す

- 依存は `vp add` / `vp remove` で足し外す ([Vite+ docs「Package Management」][] の「Add and Remove」)。素の `pnpm` / `npm` / `yarn` で足し外さない。理由は「入口を `vp` にそろえる理由」にある
- `vp` が中継しないサブコマンドだけは素の `pnpm` で打つ。`pnpm peers check` がこれに当たる (「peer の食い違いを数える」)
- 依存を外したら、その依存が必須の peer として入れていたパッケージが残っていないかを `vp why <パッケージ>` で確かめる。pnpm は optional peer を、範囲に合う版がすでに入っているときだけ入れる ([pnpm 11.x docs「Optional peer dependencies」][])。残っていたら、それを optional peer に持つ依存を `vp remove` して `vp add` し直す。2026-11-24 に pnpm 11.28.0 で、lock の写しから `eslint-plugin-testing-library` を外すと、ESLint は `@shadcn/lint` の optional peer として lock に残り (変えていない依存の optional peer が lock にある版のまま保たれた)、`@shadcn/lint` を外して入れ直すと消えた

### Void の skill を扱う

`.agents/skills/void`・`.agents/skills/migrate-vite-cloudflare-to-void` と、`.claude/skills/` の同じ名前は、`node_modules/void/skills/` への symlink である。`void init` が張る (Void 1.4.0 の `cli/init.ts` の `linkSkillsForSpecificAgents`、`cli/skills.ts`)。

- 2 つとも `void init` の出力のまま残す。移行の skill は、Void を上げたときに `void init` の出力と比べる手間を減らすために残しているもので、このリポジトリでは使わない
- symlink なので、Void を上げると中身も上がる。`skills-lock.json` には載せない。`skills-lock.json` は GitHub から写した skill (`shadcn`・`valibot`) の hash を持つもので、symlink の skill は Void の版が中身を決める
- symlink の先は `node_modules` の中なので、`vp install` の前は辿れない。辿れないことを壊れたと取らず、`vp install` のあとに見る

### 環境変数を足す

アプリが読む環境変数は、ルートの `env.ts` に `defineEnv` で宣言し、`void/env` の `env` で読む ([Void docs「Environment variables」][]、ADR-0004)。開発の道具 (タスク、スクリプト) だけが読む値は `.mise.toml` の `[env]` に置く (`docs/guides/vite-configuration.md`「タスクを足す」)。

1. `env.ts` の `defineEnv` に、名前と型を足す。型は `void/env` の `string()`・`number()`・`boolean()`・`url()`・`email()`・`oneOf([...])`・`json<T>()` か、Standard Schema の validator で書く。`.optional()` と `.default(value)` を付けられる。秘密を `default` に書かない ([Void docs「Environment variables」][] の Define the schema)
2. コードでは `import { env } from "void/env"` で読み、`env.<名前>` を使う。`process.env`・`import.meta.env` で読まない。`env.ts` の検証と型を通らない。`src/env.d.ts` の `ImportMetaEnv` には宣言しない
3. ローカルの値はルートの `.env` に書く。dev の server と `void db` などが同じ `.env` を読み、shell の値がそれに勝つ。`vp preview` の Worker が受けるのは `.env` にある名前だけである (`docs/guides/auth.md`「preview に secret を渡す」)。値に `#` を含むときは引用符で囲む ([Void docs「Environment variables」][] の Local development)
4. `vp exec void env check` を打ち、`.env` と shell の値が宣言を満たすかを確かめる。欠けた値と不正な値で exit 1 になる ([Void CLI reference「Secrets and Environment」][] の `void env check`)。dev の server は欠けを警告にしか出さず、起動は止まらない
5. 本番へ出すなら `docs/guides/deployment.md`「本番の秘密を足す」の手順で値を渡す

| 値の種類     | 判別                        | ローカル          | 本番                                                            |
| ------------ | --------------------------- | ----------------- | --------------------------------------------------------------- |
| server の値  | 名前が `VITE_` で始まらない | `.env`            | `void secret put`。`void.config.ts` の `worker.vars` に置かない |
| ブラウザの値 | 名前が `VITE_` で始まる     | `.env` (dev だけ) | build のシェルの環境変数か、schema の `default`                 |

- `VITE_` で始まる値はブラウザの JavaScript に埋め込まれるので、秘密を置かない。build は `.env` のブラウザの値を読まない。手元の値が黙って本番の設定になるのを防ぐためである ([Void docs「Environment variables」][] の Client values)
- 必須の `VITE_*` (`default` なし) を宣言すると、手元の `vp run verify` の build と CI の `verify:build` は、build の shell に値が無いと `Client env validation failed` で落ちる。`void env check` は `.env` を見るので通る。手元は `VITE_NAME=<値> vp run verify` で渡す。CI の `verify:build` は、値が秘密でないのでリポジトリの変数 (Settings の Secrets and variables → Actions → Variables) に置き、`.github/workflows/ci.yml` の step に `env: { VITE_NAME: ${{ vars.VITE_NAME }} }` を足す ([GitHub Docs「Store information in variables」][])。deploy の build にも同じ値を要る (`docs/guides/deployment.md`「本番の秘密を足す」)。値が環境で変わらないなら、`default` で持つ方が渡す先が要らない
- server の値を `worker.vars` に置くと、production の build が弾く ([Void docs「Configuration」][] の `worker`)
- `BETTER_AUTH_SECRET` は `env.ts` に宣言しない。宣言すると `void secret put BETTER_AUTH_SECRET` で値を検証して渡せるが、deploy が作るので要らない (ADR-0004)。preview への渡し方は `docs/guides/auth.md`「preview に secret を渡す」にある
- `.env` は Git に入れない。`.gitignore` の `.env` / `.env.*` が覆う
- `.env` 以外の dotenv ファイル (`.env.local`・`.env.production`・`.dev.vars`) は Void が扱わない ([Void docs「Environment variables」][] の Local development)。暗号化した env ファイルを commit する形は、Void が読まないので使えない
- Vite の `.env` 読み込みは `envDir: false` で切ってあり、`.env` の読み手は Void の 1 つである (ADR-0004)

### Dependabot の alerts を有効にする

テンプレートから作ったリポジトリで、Dependabot の alerts と security updates を有効にする (ADR-0005)。この設定はコードに現れない。

```bash
gh api -X PUT /repos/<owner>/<repo>/vulnerability-alerts
gh api -X PUT /repos/<owner>/<repo>/automated-security-fixes
```

### security update の PR が来ないときに job を読む

alert があるのに security update の PR が来ないときや、security update の PR の rebase が「Dependabot can't resolve your JavaScript dependency files」で止まったときは、Dependabot の job のログで理由を読む。

```bash
gh run list --workflow 'Dependabot Updates'
gh run view <run の ID> --log | grep -E 'Handled error|security_update_not_possible|latest-resolvable-version|lowest-non-vulnerable-version'
```

| ログの行                                                                                                   | 原因                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                            | 扱い                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                 |
| ---------------------------------------------------------------------------------------------------------- | ----------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------- | -------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------- |
| `dependency_file_not_resolvable` と `pnpm resolved <pkg> to <版>, above the requested <版>`                | 推移依存の最新版が `minimumReleaseAge` の待機の中にある。dependabot-core の eda07d97 (2026-11-04 の commit) のソースでは、Dependabot は pnpm の推移依存の版を選ぶときに待機を外さず (npm の経路は `--min-release-age=0` を渡す。[dependabot-core「subdependency_version_resolver.rb」][])、lockfile を書き換えるときは security update の待機を 0 にして最新版まで解決し ([dependabot-core「pnpm_lockfile_updater.rb」の待機][])、選んだ版を超えた結果を拒んでいた ([dependabot-core「pnpm_lockfile_updater.rb」の verify_unpinned_updates!][]) | すぐ直すなら、`vp update <pkg>` で lockfile を上げた PR を作る。手元の解決は `minimumReleaseAge` に従い、待機の外の最新版で止まる (2026-11-04 に pnpm 11.28.0 で systeminformation と ip-address に観測)。Dependabot に作らせるなら、`npm view <pkg> time --json` で今の最新版の待機が明けたことを確かめてから、alert の詳細画面の「Create Dependabot security update」で job を起こし直す ([GitHub Docs「Viewing and updating Dependabot alerts」][])。ログの版のあとに新しい版が出ていると、ログの版から数えて押しても同じ理由で落ちる。失敗した job を Dependabot が自分で起こし直すかは docs に書かれていないので、待たない。止まったのが既存の PR の rebase で、差分が lockfile の対象の依存の行だけなら、今の `main` に差分を当てて `vp install --frozen-lockfile` と `pnpm peers check` が通れば、rebase せずに取り込める (2026-11-04 に pnpm 11.28.0 で観測) |
| `security_update_not_possible` と、`latest-resolvable-version` が `lowest-non-vulnerable-version` より低い | Dependabot の解決が修正版に届かない。確かめた原因は 2 つある。親の範囲が修正版を受けないこと (修正版が次の major にしか無い、親が版を固定している) と、更新したあとも同じ依存の古い版が別の経路に残ること (eda07d97 のソースでは、Dependabot は推移依存の同じ依存が複数の版で入っていると、低い方の版を代表にしていた。[dependabot-core「dependency_set.rb」][])。どちらにも当たらない場合もありうる                                                                                                                                            | 親の範囲は `vp why <pkg>` と親の `package.json` の依存の宣言で読む。範囲が修正版を受けるなら、`vp update <pkg>` のあと `vp dedupe` で lockfile を解き直した PR を作る (2026-11-04 に pnpm 11.28.0 で seroval に観測)。受けないなら、親が範囲を広げるのを待つ                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                         |

### 待機を前倒しする

公開後 3 日を待たずに取り込みたいときは、そのバージョンが公式のリリースパイプラインから出たものかを確かめる (ADR-0005「前倒しは provenance を確認してから」)。

```bash
curl -s https://registry.npmjs.org/<pkg>/<version> | jq '{_npmUser, repository, attestations: .dist.attestations}'
curl -s "https://registry.npmjs.org/-/npm/v1/attestations/<pkg>@<version>"
```

1. `_npmUser` に `trustedPublisher` があれば OIDC による公開である。個人トークンでの公開は、トークンの漏洩が成立経路になるので、前倒しの根拠に足りない
2. attestation の `subject` が対象の package と version に一致し、`workflow.repository` が公式のリポジトリで、`workflow.ref` が既定のブランチかリリースタグであることまで見る
3. `pnpm-workspace.yaml` の `minimumReleaseAgeExclude` へ、バージョンまで固定して (`@scope/pkg@x.y.z`) 追記する

追記したエントリの後始末は、`pnpm-workspace.yaml` で有効にした `minimumReleaseAgeExcludePrune` が持つ。`vp add` / `update` / `remove` のたびに、lockfile が解決しなくなったエントリが消え、`@scope/*` の形のパターンは残る ([pnpm docs「minimumReleaseAgeExcludePrune」][])。

### peer の食い違いを数える

```bash
pnpm peers check
```

- lockfile を読んで、宣言された peer の範囲と入っている版の食い違いを数える ([pnpm docs「pnpm peers」][] の check)。lockfile は書き換えない
- 素の `pnpm` で打つ。2026-09-28 に vite-plus 1.0.0 で、`vp pm` は `peers` を中継しなかった (`vp pm peers check` は `Command 'peers' not found`)
- `vp install` の出力が静かでも、食い違いが無いとは限らない。lockfile が最新なら install は解決を走らせず、peer の食い違いを報告しない ([pnpm/pnpm#14114][])
- 許可を外すだけでは lockfile が変わらないので、2026-09-29 に pnpm 11.28.0 で、`--force` を付けても `strictPeerDependencies: true` にしても install は通り、食い違いを出したのは `pnpm peers check` だけだった
- 食い違いを許すなら、`pnpm-workspace.yaml` の `peerDependencyRules.allowedVersions` に親つきのキー (`"<親>><peer>": "<range>"`) で書き、理由と撤去条件をコメントに残す。`*` や親なしのキーにすると、版が上がって新しく食い違っても見えなくなる
- 値の range は、確かめた版の major にする (`"1"`)。0.x の依存だけは minor までにする (`"^0.153.0"`)。0.x は minor で破壊的変更を入れることが多く ([node-semver README「Caret Ranges」][])、`"0"` は 1.0.0 未満のすべてを満たして ([node-semver README「X-Ranges」][])、食い違いを黙らせる。値の書き方は [pnpm docs「peerDependencyRules.allowedVersions」][]
- 撤去条件は、pin の出口条件と同じく上流の修正かリリースで書き、Dependabot の PR を処理するときに確かめる (ADR-0005「pin には出口条件を書く」)
- Vite+ を上げたら、`vite-plus/versions` の export が残っているかを確かめる。`storybook>vite-plus` の許可は値を major にしたので、export が消えても `pnpm peers check` は鳴らない
- storybook を上げたら、dist が `vite-plus` から import しているものを読み直す。`storybook>vite-plus` の許可は、storybook が `vite-plus/versions` だけを読むことを前提にしている (2026-11-24 に `storybook@10.6.8` の dist で確認)
- キーの親に版を付けない (`"<親>@<版>><peer>"` にしない)。pnpm 11 の `pnpm peers check` は親の版を捨て、名前だけで照合する。install は親の版を見るので、2 つの判定が割れる (2026-09-29 に 11.28.0 で実測。同じ日に見た 12.6.0 の `pnpm peers check` は親の版を見ていた)
- 許可した側を値の range の外へ上げると (1.0.0 以上は major、0.x は minor)、`pnpm peers check` に再び食い違いとして出る。新しい版で動くことを確かめ直してから、値を書き換える
- 親を上げたら、そのエントリの撤去条件を見る。どのエントリが何を待っているかは `pnpm-workspace.yaml` のコメントが持つ
- 一緒に上げる依存の組は、`.github/dependabot.yml` の組のグループで 1 本の PR にする (ADR-0005)。組を足すときは、patterns を `minor-and-patch` の `exclude-patterns` にも写す (「Vite+ を上げる」の `minor-and-patch` の項目)
- 組の major を見送るときは、組の依存ごとに `dependency-name` と `update-types: ["version-update:semver-major"]` の `ignore` を足し、撤去条件をコメントに書く (ADR-0005「pin には出口条件を書く」)。グループの PR を閉じても、Dependabot は今の major の中の更新を別に出さない (ADR-0005)
- security update の PR は、脆弱な依存だけを上げる (ADR-0005)。`verify:peers` で落ちたら、その PR のブランチで組の相手を peer が求める版へ上げてから取り込む。ブランチに commit を足すと Dependabot は rebase しなくなる ([GitHub Docs「Managing pull requests for dependency updates」][])。組の version update の PR がその版以上へ上げたなら、そちらを取り込む。依存が修正版に届くと、Dependabot が security update の PR を閉じる (2026-10-30、"Looks like @storybook/addon-vitest is up-to-date now, so this is no longer needed.")
- `@vitejs/plugin-react` と `oxc-transform-react` は、`.github/dependabot.yml` の `react-compiler` グループで 1 本の PR にする。plugin-react は optional peer の oxc-transform-react を呼び出す。別々の PR に割れると、上流が試していない組み合わせが片方ずつ入る
- グループの PR でも、組の片方だけが上がり、`verify:peers` で落ちることがある。dependabot-core の eda07d97 のソースでは、Dependabot は、上げる依存が関わる peer の食い違いを、版を選ぶ判定から外していた。上げる依存自身もグループに属するので、食い違いの相手がグループの内か外かを問わなかった ([dependabot-core「version_resolver.rb」][])。落ちた PR は、CI の `verify:peers` の出力 (`Installed` の版、`Wanted` の範囲、範囲を宣言する依存) を読み、範囲を満たす組み合わせが公開されているかを探す。PR が peer の相手を上げたなら `npm view '<宣言する依存>@><今の版>' peerDependencies.<相手>` で、宣言する依存を上げたなら `npm view '<相手>@<Wanted の範囲>' version` で探す
  - 見つかった版が cooldown の中 (公開日時は `npm view <pkg> time --json`、cooldown は `.github/dependabot.yml`): 2026-11-04 のログでは、グループの PR を更新する実行が、PR に載っていない組の相手も cooldown の外の版から選び直していた (`Checking if @vitejs/plugin-react 6.1.2 needs updating` と `Filtered out 2 versions due to cooldown`)。cooldown が明けたあとの実行の CI で、揃ったかを見る。待たずに揃えるなら、「待機を前倒しする」の手順で組の両方を上げた PR を自分で作り、それを merge してから Dependabot の PR を閉じる
  - 見つからない: PR を開いたまま置き、上流が peer を広げるのを待つ。閉じても次の実行で作り直される (ADR-0005)。PR の版に、このリポジトリのコードの変換や実行に効く不具合の修正 (React Compiler の誤変換など) が入っているなら、待たずに親つきのキーで許して取り込む。値は確かめた版の major (0.x は minor) までにし、撤去条件は上流のリリースで書く (この節の上の項目)。取り込む前に `vp run verify` を通す
- `vitest` の `allowAny` と `allowedVersions` の行は例外で、2026-11-24 に vite-plus 1.7.0 で、`vp migrate` が書き、消しても書き戻した
- `vitest` の行は効いていない。`overrides` の `vitest@*` は `catalog:` を指し、catalog を指す override は peer の宣言も置き換える ([pnpm docs「Overriding peer dependencies」][])。`vitest` の peer の食い違いは `pnpm peers check` に出ない
- `vite` の行は置かない。core の版が同梱の Vite の版を表す (`8.3.8000` は Vite 8.3.8) ので、`vite` を peer に持つ依存の範囲を満たす。`vp migrate` は `vite` の行を消す ([Vite+ docs「Migration Rules」][])。行の無いまま `pnpm peers check` は食い違いを出さなかった (2026-11-24、vite-plus 1.7.0、pnpm 11.28.0)
- `vite` の peer の範囲が同梱の Vite を含まない依存は、`pnpm peers check` に食い違いとして出る。その依存を上げるか、親つきのキー (`"<依存>>vite"`) で許す ([Vite+ docs「Migration Rules」][])

### 依存をバレルの禁止の対象に足す

対象に足すかは ADR-0032 の基準で決める。手順は次のとおり。実例は `tooling/lint/config.ts` の `RESTRICTED_BARREL_IMPORTS` の date-fns の 2 行。

1. 依存の `package.json` の `exports` を読み、個別エントリポイントがあるかと、バレルがどれか (ルートの `.`、`./locale` のようなまとめ) を確かめる。個別エントリポイントが無い依存は対象にできない
2. バレルから 1 つだけ import するテストと、同じものを個別エントリポイントから import するテストを 1 ファイルずつ `src/lib/` に一時的に置く。Node で読むなら `.test.ts`、ブラウザで読むなら `.test.tsx`
3. テストファイルの `collectDuration` を出す reporter を、リポジトリの外 (例: `/tmp/collect-reporter.mjs`) に一時的に置く。Vitest 5 の `Duration` の行は phase を割合で出し、import の時間を ms で出さない。CLI でパスを渡す reporter は、default export をクラスにする

   ```js
   export default class {
     onTestRunEnd(testModules) {
       for (const m of testModules)
         console.log(m.moduleId, Math.round(m.diagnostic().collectDuration));
     }
   }
   ```

4. ほかの重い処理を止めてから、1 ファイルずつ `vp test run --project <unit か browser> <ファイル> --experimental.importDurations.print --experimental.importDurations.limit=10 --reporter=default --reporter=<reporter のパス>` を、バレルと個別エントリポイントで 1 回ずつ交互に、5 回ずつ続けて実行する。交互にすると、途中で負荷が変わっても片方にだけ載らない。回ごとに、reporter が出す `collectDuration` と、内訳が出れば `Total import time` の self を控える。`Total import time` の total は入れ子の import を二重に数えるので使わない (ADR-0032 の「調査結果」)。browser project は、依存の事前バンドルのキャッシュを作る最初の実行を比較から外す
5. `collectDuration` について、比較する回の中央値の差が、両者の最大と最小の差の和を超えるかを見る。上の 5 回ずつを 1 群として 3 群測り、2 群以上で超えなければ足さない。大きく延びた回があるとばらつきが広がり、差があっても 1 群では超えないことがある
6. 足すなら `RESTRICTED_BARREL_IMPORTS` に `{ name, message }` を 1 つずつ足す。`name` は specifier の完全一致で、サブパス (`date-fns/format`) は止めない。`message` には個別エントリポイントの例と `(ADR-0032)` を書く
7. `vp lint -f unix src scripts .storybook` で、足した依存のバレルを import している箇所を洗い出し、個別エントリポイントへ直す
8. 一時的に置いたテストと reporter を消す

- 依存の中の import (ある依存が別の依存のバレルを読む経路) は lint が届かない。テストを遅くしているかは、その依存を描くテストを同じ手順で測る
- `RESTRICTED_BARREL_IMPORTS` はトップレベルと、`no-restricted-imports` を書くすべての override へ渡っている。定数に足し、どれか 1 つの `paths` にだけ書き足さない。`no-restricted-imports` を書く override を足したら、その override にも渡す (`docs/guides/lint/configuration.md`「設定の落とし穴」)

### Vite+ を上げる

Dependabot は `vite-plus` の更新を `vite-plus` グループの PR にする。`vitest` と `@vitest/*` は `ignore` してあり、bot は上げない。脆弱性は alert で届く (ADR-0005)。`vite-plus` の PR が来たら、そのブランチで次を打つ。

```bash
gh pr checkout <PR 番号>
vp install
vp exec vp migrate --no-interactive
vp run verify
git diff pnpm-workspace.yaml  # catalog に依存が増えていたら、この節の catalog の項目で .github/dependabot.yml を見直す
git add -A
git commit -m "vp migrate で core と vitest を vite-plus の同梱の版へ揃える"
git push
```

- `vp migrate` は、打った CLI が同梱する版へ core と `vitest` を揃える ([Vite+ docs「Update Vite+」][])。直接の依存にある `@vitest/*` も `vitest` の版へ揃える ([Vite+ docs「Migration Rules」][])。先に `vp install` で PR の版の `vite-plus` を `node_modules` へ入れ、`vp exec` でその CLI を打つ
- `vp migrate` は変えたファイルを `vp fmt` で整える。migrate の前から変更のあったファイルは整えない ([Vite+ docs「Migration Rules」][])。2026-09-29 に vite-plus 1.0.0 で、キーの順序とコメント、テンプレートが足したキーと行は残った
- `pnpm peers check` の食い違いと、`storybook>vite-plus` の許可が頼る `vite-plus/versions` の export は「peer の食い違いを数える」で確かめる
- push したあとは、Dependabot がその PR を rebase しなくなる ([GitHub Docs「Managing pull requests for dependency updates」][])。`main` が進んだら手で取り込む
- Dependabot の PR を処理するときは、`vite-plus` の PR が止まっていないかを確かめる (ADR-0005)。`npm view vite-plus time --json` で latest の公開日時を見て、cooldown (`.github/dependabot.yml`) を過ぎたあとの Dependabot の実行 (`gh run list --workflow 'Dependabot Updates'`) で `vite-plus` の PR ができていなければ、その実行のログで判定を見る。`gh run view <run の ID> --log | grep -E "Updating vite-plus from|No update needed for vite-plus"`
- `minor-and-patch` は `exclude-patterns` で、patterns を持つほかのグループの依存をすべて除く。patterns を持たないグループは、他のグループに入った依存も抱え込む (2026-09-29 時点、[dependabot/dependabot-core#14576][])。写さないと、組の依存が組のグループから外れて `minor-and-patch` の PR に入るか、両方のグループに入り、組が 1 本の PR にそろわない。2026-09-28 には `vitest` が両方のグループの PR に載った
- `vp migrate` が `pnpm-workspace.yaml` の catalog に、`.github/dependabot.yml` の `vite-plus` グループの `patterns` に当たらない依存を足したら、その `patterns` と `minor-and-patch` の `exclude-patterns` にも足す
- `vp migrate` が catalog に足した依存が、`vitest` のように `vite-plus` と別の日に公開され、既存の `ignore` に当たらないなら、`ignore` にも `dependency-name` だけで足す (ADR-0005)。撤去条件の書き方は「pin を足す」

### pin を足す

pin を足すときは、ADR-0005「pin には出口条件を書く」に従って出口条件を書く。間接的に pin の圏内へ入るパッケージを見つけたら `ignore` へ足し、同じ出口条件を参照させる。出口条件の文字列を grep すれば、pin の全構成要素が見つかる状態を保つ。

### patch を当てる

依存の配布物に patch を当てるときは、`vp pm patch <pkg>` を版を付けずに打つ。2026-11-23 に読んだ pnpm 11.28.0 の `pnpm11/patching/commands/src/getPatchedDependency.ts` では、版を付けずに打ち、入っている版が 1 つなら、`pnpm-workspace.yaml` の `patchedDependencies` にパッケージ名だけのキー (`"<pkg>"`) で足していた。このキーはどの版にも当たる ([pnpm docs「pnpm patch」][] の patchedDependencies、「patch のキーをパッケージ名だけにする理由」)。そのキーの直前のコメントに、理由と撤去条件 (ADR-0005「pin には出口条件を書く」) と、効いていることの確かめ方を書く。`vp run verify` が捕まえない patch もあるので、確かめ方が無いと壊れても気づけない。

- 作り直すときも版を付けずに打つ。2026-10-01 に pnpm 11.28.0 で、版を付けずに打つと既にある patch を当てた編集用のディレクトリができ、`vp pm patch-commit` は同じキーと同じファイルへ書き戻した。版を付けると既にある patch が当たらず、`patch-commit` は版を固定したキーを足して `ERR_PNPM_UNUSED_PATCH` で落ちた。その案内どおりにパッケージ名だけのキーを消すと、元の変更が黙って消えた
- `vp pm patch-commit` したあとは、初めて作ったときも作り直したときも、`pnpm-lock.yaml` を HEAD の内容へ戻してから `vp install` する。`patch-commit` を通った lockfile では、patch を当てた依存の `optionalDependencies` が落ちていた (2026-10-01 に pnpm 11.28.0 で観測)

### workflow に action を足す

- step の `uses:` は `@vX.Y.Z` で書き、commit は `.github/workflows/actions.lock` に記録する (ADR-0006)。`@v4` のような部分の版と `@<SHA>` は、初めて固定するときに `gh actions-lock` が `@vX.Y.Z` に書き換える
- workflow を足したとき、`uses:` を足す・変える・消したときは、リポジトリのルートで `gh actions-lock` を打ち、workflow と `actions.lock` を同じ commit に入れる。打ち忘れると、lockfile に entry の無い action を使う workflow は、job を 1 つも始めずに `startup_failure` で止まる。原因の action は `actions-lock` の job のログに `Not pinned` で出る (ADR-0006)
- どの workflow も job を始めずに `startup_failure` で止まったら、手元で `gh actions-lock --verify` を打ち、`Not pinned` と出た action を確かめる。`actions-lock.yml` が使う action の entry が欠けると、`actions-lock` の job 自身も始まらず、ログに何も出ない (ADR-0006)
- 拡張は `gh extension install github/gh-actions-lock --pin <版>` で入れ、`<版>` は `.github/workflows/actions-lock.yml` の `--pin` と同じにする。新しい拡張が書いた lockfile の `version` を CI の拡張が読めないと、verify の job が exit 2 で落ちる ([gh-actions-lock「troubleshooting」][] の「Lockfile version is newer than the extension」)
- 別のリポジトリの reusable workflow の呼び出し (`jobs.<job_id>.uses`) は、lockfile が記録しないので `@<SHA> # vX.Y.Z` で書く (ADR-0006)。手元で `zizmor --fix=all` を使うと SHA へ書き換わる。SHA 固定は unsafe fix に分類され、既定の `--fix=safe` では書き換わらない
- このリポジトリに置く composite action は、workflow から `uses: $/<path>` で呼ぶ。ほかの action を使う composite action を `./<path>` で呼ぶと、`gh actions-lock` が `local-action` で止まる。workflow の `./<path>` は `gh actions-lock --migrate-local-actions` が `$/<path>` へ書き換えるが、`action.yml` の中の `./<path>` は書き換えないので手で直す ([gh-actions-lock「troubleshooting」][] の `local-action`、ADR-0006)
- composite action の定義 (`action.yml`) の中の `uses:` は `@<SHA> # vX.Y.Z` で書く。ほかのリポジトリがこの action を使うと、こちらの lockfile が効かない。zizmor の `unpinned-uses` も、composite の step を lockfile と関係なく指摘する (ADR-0006)
- container image (`docker://`、job の `container:` と `services:`) は lockfile が記録しないので、`@sha256:<digest>` で書く (ADR-0006)
- `actions.lock` を手で書き換えず、消さない。壊したら default branch の版を `git checkout origin/main -- .github/workflows/actions.lock` で戻してから `gh actions-lock` を打つ。消して作り直すと、すべての ref をそのときの commit で解き直し、付け替えられた tag も警告なしに受け入れる ([gh-actions-lock「troubleshooting」][] の「Why you shouldn't delete the lockfile」)
- `gh actions-lock --verify` が `tag-commit-mismatch` で落ちたら (記録した exact tag が、記録した commit より後の commit へ動いた)、lockfile が手で書き換えられていないかと、上流の 2 つの commit の間の変更を確かめてから `gh actions-lock --relock` を打つ ([gh-actions-lock「troubleshooting」][] の `tag-commit-mismatch`)
- `unreachable-pin` で落ちたら (記録した commit が ref の履歴から外れた。force push、無関係な commit への tag の付け替え、lockfile の手の書き換えのどれか)、上流の履歴と release notes を記録した commit と比べ、正しいと確かめてから手元で `gh actions-lock --accept-moved` を打つ。CI と bot の中では打たない ([gh-actions-lock「troubleshooting」][] の `unreachable-pin`)
- zizmor に新しい audit が入ると、action の更新 PR で既存の workflow が落ちうる。その PR の中で直すか、`.github/zizmor.yml` で理由を書いて無効にする

### 走査対象を持つ config を足す

`tooling/test/config.ts` (test。project はここから継承する) / `tooling/lint/config.ts` (lint) / `vite.config.ts` (fmt) は、それぞれ `.claude/worktrees/**` を除外している。`tsconfig.*.json` は `.claude/worktrees/**` の除外を持たない。どの `include` もルートの直下の名前 (`src/**/*.ts`・`scripts/**/*.ts` など) から書くので、`.claude/` を拾わない。TypeScript の `include` の `**` は `.` で始まるディレクトリに降りない (TypeScript 6.0.3 の `lib/typescript.js` の `doubleAsteriskRegexFragment` が、ディレクトリ名を `[^/.][^/]*` に限る)。2026-11-03 に `src/.<名前>/x.ts` を置くと `tsc -p tsconfig.app.json --listFilesOnly` に出ず、同じファイルを `.` で始まらないディレクトリに置くと出た。`.` で始まるディレクトリのファイルを型検査に入れるときは、`.storybook/preview.tsx` のように字面で書く。走査対象を持つ config を新しく足したら、同じ除外をその場で書くか、その config の glob が `.claude/` に降りないことを確かめる。除外の経路は config ごとに別で共通化できず、1 つ落とすと worktree のコードがその走査へ黙って混ざる。

### `git status` に出ないファイルを調べる

作ったファイルが `git status` に出ないときは、`git check-ignore -v <パス>` で、当たった `.gitignore` の行を見る。

- `.gitignore` の、先頭と途中に `/` を含まない行 (`out`、`pids`、`.cache` など) は、どの深さの同じ名前のディレクトリにも当たる ([gitignore(5)][])。そこに作ったファイルは、`git add .` では何も言われずに飛ばされ、パスを名指しした `git add` では拒まれる ([git-add(1)][])
- 外すときは、`.gitignore` の末尾に `!src/<ディレクトリ>/out/` のように、当たったディレクトリのパスを足す。親のディレクトリが除外されていると、中のファイルを名指しした `!` は効かない ([gitignore(5)][])。当たった行が使わないツールのもの (Next.js の `out` など) なら、行ごと消してもよい

## explanation

### `typescript` を直接の依存に置かない理由

`vp check` の型検査は oxlint の type-aware パスが担い、その実体は tsrs (TypeScript 7 のコンパイラを Rust へ移したもの) の `tsrs-lint` である ([Vite+ docs「Check」][]、[Vite+ docs「Lint」][])。tsrs は `vite-plus` が依存として入れ、`typescript` パッケージに依存していなかった (2026-11-23 に読んだ `tsrs@7.1.0-beta.tsrs2` の依存は、プラットフォームごとのバイナリだけだった)。
`typescript` パッケージは `@voidzero-dev/vite-plus-core` や Storybook、typescript-eslint の推移依存として入るので、直接の依存から外しても install からは消えない (2026-11-24 に vite-plus 1.7.0 で `pnpm why typescript`)。同じ日に、直接の依存に置かないまま型の誤りを置いて `vp check` を走らせると、`TS2322` を報告した。
直接の依存へ戻すのは、リポジトリのコードが `typescript` を `import` するようになったときだけでよい。リポジトリのコードが使わないパッケージを、直接の依存として宣言しない。

型検査の範囲は lint の対象と同じで、tsconfig の `include` に入る TS のファイルを lint の対象から外すと、そのファイルは型検査されない ([tsrs の README「Type-aware lint」][])。別に型検査を走らせる条件と打ち方は ADR-0047「型検査の実行」にある。
型検査を lint へ合流させる設定 (`options.typeCheck`) は `scripts/checks/integrity/lint-config.test.ts` が解決後の設定の値で押さえるが、設定が真のまま tsrs が黙って動かない場合は捕まえられない。

### patch のキーをパッケージ名だけにする理由

版まで固定したキーは、上げた版には使われず、install が `ERR_PNPM_UNUSED_PATCH` で落ちる (`allowUnusedPatches` の既定は `false`。[pnpm docs「pnpm patch」][])。この失敗は、lockfile だけを更新するとき (`install --lockfile-only`) にも起きる (2026-10-01 に pnpm 11.28.0 で観測)。2026-09-30 と 2026-10-01 に読んだ dependabot-core の d4120cab のソースでは、Dependabot は pnpm を `--lockfile-only` で走らせ ([dependabot-core「pnpm_lockfile_updater.rb」][])、失敗した依存を飛ばして残りで PR を作っていた ([dependabot-core「group_update_creation.rb」][])。その依存だけが黙って PR から抜け、揃えて上がる依存の版が割れる。範囲のキー (`"<pkg>@^<版>"`) も、範囲の外へ上げた版には使われないので同じことになる。

パッケージ名だけのキーは、どの版にも当てる ([pnpm docs「pnpm patch」][])。当たらなければ通常の install が `ERR_PNPM_PATCH_FAILED` で落ち、`--lockfile-only` では落ちない (2026-10-01 に pnpm 11.28.0 で観測) ので、Dependabot の PR は作られ、その PR の CI で気づける。Dependabot の振る舞いはコードで確かめ、実行では観測していない。同じ docs には、名前だけのキーは当たらない失敗を無視すると読める記述もあるが、v11 では当たらない失敗は常にエラーになる (同じ docs の `allowUnusedPatches` の注記)。ただし patch 適用の実装 (`@pnpm/patch-package` の `applyPatch`) は、前向きに当たらなくても逆向きの dry-run が当たれば成功として扱う (pnpm/patch-package の `src/applyPatches.ts` のソースの読み取りで、実行では観測していない)。修正済みの版へ上げても落ちずに静かに通ることがあるので、落ちないことを patch が不要になった証拠にしない。

作り直しの手順も短くなる。`vp pm patch` を版を付けずに打つと、パッケージ名だけのキーの patch を編集用のディレクトリに当て、`patch-commit` は同じキーと同じファイルへ書き戻す。範囲のキーの patch は `vp pm patch` が当てず、`patch-commit` は範囲のキーとは別のキーとファイルを足すので、作り直すたびに元の patch を当て直し、キーとファイルを手で直すことになる (2026-10-01 に pnpm 11.28.0 で、両方のキーについて観測)。

### 入口を `vp` にそろえる理由

- [Vite+ docs「Package Management」][] は、`vp` がプロジェクトの package manager を見分けて走らせ、`vp install` / `vp add` / `vp remove` を package manager をまたいだ共通の入口にする ("Instead of switching between `pnpm install`, `npm install`, `yarn install`, and `bun install`, you can keep using `vp install`, `vp add`, `vp remove`")。打つ側がプロジェクトの package manager を覚えなくてよい
- `npm` と `yarn` は pnpm に翻訳されない (同 docs: "Mismatched tools are not translated; `npm` in a `pnpm` project still resolves as npm.")。このリポジトリの `package.json` は `catalog:` を使うので、npm は依存を解決できない。2026-10-02 に npm 11.19.0 で、このリポジトリの `package.json`・`pnpm-lock.yaml`・`pnpm-workspace.yaml`・`patches` を写した場所で `npm install is-odd@3.0.1 --package-lock-only` を打つと、`npm error code EUNSUPPORTEDPROTOCOL` (`Unsupported URL Type "catalog:"`) で止まり、`package-lock.json` を作らず `pnpm-lock.yaml` も変わらなかった。`yarn` は測っていない
- 素の `pnpm` は結果を変えない。shim が `packageManager` の版 (pnpm 11.28.0) に解決する ([Vite+ docs「Environment」][])。2026-10-02 に vp 1.0.0 で、`~/.vite-plus/bin` の `pnpm` / `pn` / `pnpx` / `pnx` は `vp` への symlink で、リポジトリで `pnpm --version` は 11.28.0 を返した。同日に、このリポジトリの `package.json`・`pnpm-lock.yaml`・`pnpm-workspace.yaml`・`patches` を写した場所で `vp add is-number@7.0.0 --lockfile-only` と `pnpm add is-number@7.0.0 --lockfile-only` を打つと、同じ `package.json` と `pnpm-lock.yaml` を作った。`pnpm` も止めるのは lockfile のためではなく、入口を `vp` の 1 つにそろえるためである
